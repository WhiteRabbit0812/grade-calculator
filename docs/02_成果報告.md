## 一、學習內容與執行過程

### 練習的程式

這次拿來練習的是我大一寫的成績計算程式 src/grade.py。它有五個函式：average 算平均、letter 把分數換成 A 到 F、gpa 算 GPA、load_csv 讀「姓名,分數」格式的檔案，最後 report 把結果整理成一份文字報表。

### 我怎麼做的

我先把舊程式原封不動放進 Git，當作改之前的基準。接著針對每個函式寫測試，寫完先不改程式，直接跑一次，把結果存成 docs/test_before.txt。然後照著失敗的測試一個一個修，修完再跑一次，存成 docs/test_after.txt。最後寫 GitHub Actions 的設定檔，推上 GitHub 讓它自動跑。

每個階段都有 commit，在 GitHub 上看 commit 紀錄就能看出這個順序：先放舊程式，再加測試，然後才修正。

### 測試怎麼設計

我對每個函式都想三種情況：正常的輸入、剛好在邊界上的輸入、不合理的輸入。

花最多心思的是 letter。等第有四個門檻，我每個門檻都測「剛好」和「差一分」，例如 90 應該是 A、89 應該是 B、60 應該是 D、59 應該是 F，另外 -1 和 101 應該要直接報錯。這十組資料如果每組寫一個函式會很冗長，所以我用了 pytest 的 parametrize，一個測試函式搭配一張資料表就搞定。

average 和 gpa 除了一般資料，還多測了「完全沒有成績」的情況。load_csv 則是用 pytest 的 tmp_path 在測試裡臨時建檔，分別測正常的檔案、有空白行和多餘空格的檔案，以及分數不是數字的檔案。

總共寫了 22 個測試。

完整的輸出放在 docs/test_before.txt。

### 找到的問題

這 10 個失敗整理起來是四類問題：

| 問題 | 原因 | 會造成什麼影響 |
|---|---|---|
| 剛好 90、80、70、60 分的等第會少一級 | 判斷時用了 > 而不是 >= | 60 分被判成 F，等於及格的人被當掉 |
| 沒有成績時程式會當掉 | 直接除以 len(scores)，空的時候變成除以 0 | 空檔案沒辦法產生報表 |
| -1、101 這種分數照樣被接受 | 沒有檢查分數範圍 | 打錯的資料會被當成正常成績算進去 |
| 檔案有空白行或多餘空格會當掉 | 切字串前沒有先去掉空白，也沒跳過空行 | 從 Excel 匯出的 CSV 最後常常會多一行空白，很容易遇到 |

最讓我意外的是第一個。其實我一開始用範例資料跑程式時，畫面上就印出「陳大文 60 F」，只是我完全沒注意到。如果沒有專門針對 60 分寫測試，這個錯可能會一直留著。

除此之外，我也發現舊程式用 open() 開了檔案卻沒關，順手改成 with open() 的寫法。

我把門檻、等第和點數放進同一張表，兩個函式都從這張表查：

```python
GRADE_TABLE = [
    (90, "A", 4),
    (80, "B", 3),
    (70, "C", 2),
    (60, "D", 1),
    (0, "F", 0),
]

def letter(score):
    if score < 0 or score > 100:
        raise ValueError("分數必須介於 0 到 100：" + str(score))
    for lower, grade, _ in GRADE_TABLE:
        if score >= lower:
            return grade
```

這樣改的原因很單純：以後如果要改門檻或加一個等第，只要改這張表就好。原本的寫法要改兩個地方，很容易只改到一邊。這次敢動手整理，也是因為已經有測試在。改完重跑一次，全部通過，就知道沒改壞。

### GitHub Actions

設定檔放在 .github/workflows/test.yml。只要 push 到 main，或有人對 main 發 Pull Request，GitHub 就會自動用 Python 3.10、3.11、3.12 各跑一次全部的測試。我還加了一個條件：覆蓋率低於 90% 就算失敗，避免以後加了新功能卻忘了寫測試。

推上 GitHub 後第一次執行，三個版本都通過了，每個版本大約十幾秒就跑完。

## 四、遇到的困難及解決方法

一開始測試檔一直 import 不到 grade。原因是程式放在 src 資料夾，測試放在 tests 資料夾，pytest 預設找不到 src 裡的東西。我先在測試檔開頭把 src 加進 sys.path 解決，後來查資料才知道也可以在 pyproject.toml 裡設定 pythonpath，那應該是比較正規的做法，下次會試試看。

再來是不知道怎麼測讀檔的函式。我本來想在專案裡放好幾個測試用的 CSV，後來在 pytest 文件裡看到 tmp_path，可以在測試當下建一個暫存檔，測完自動刪掉，乾淨很多。

在 Windows 的終端機跑測試時，中文一直顯示成亂碼。後來把環境變數 PYTHONIOENCODING 設成 utf-8 就正常了。也是因為這件事，我回頭確認程式讀檔時有指定 encoding="utf-8"，不然換一台電腦可能就讀不出中文名字。

心態上也有一個小插曲。第一次跑出 10 個失敗的時候，我的第一個反應是「是不是我的測試寫錯了」。後來一個一個對照規則才確定是程式的問題，例如學校規定 60 分及格，程式卻判成 F。這讓我體會到，測試的預期結果要根據規格來定，不能看程式現在輸出什麼就寫什麼。

最後是推上 GitHub 之後，Actions 雖然全部通過，但跳出一則警告，說我用的 actions/checkout@v4 和 actions/setup-python@v5 還在用 Node.js 20，而 Node.js 20 即將停用。我查了這兩個 action 目前的版本，發現都已經出到 v7，而且改用 Node.js 24，就把設定檔裡的版本號改掉，重新推一次，警告就消失了。這件事讓我發現，CI 的設定寫好之後並不是就不用管了，用到的工具也會更新，要跟著維護。

## 五、學習成果、限制與個人反思

### 學到了什麼

這次我學會了 pytest 的基本用法，包括參數化測試、測試會不會丟出錯誤，以及用暫存檔測讀檔的函式。我也實際用了 pytest-cov 看覆蓋率，並學會設定 GitHub Actions，讓測試在每次 push 時自動執行。

回頭看計畫書裡的三個問題：

第一個問題的答案是「能，而且找到不少」。一支我以為沒問題的程式，補完測試就找到四類錯誤。

第二個問題，我的結論是覆蓋率只能當參考。95% 只代表這些程式碼有被執行到，不代表每種情況都測過了。例如姓名重複、一行有三個欄位，這些我都還沒測，但覆蓋率完全反映不出來。

第三個問題已經做到了，而且我還遇到工具版本更新的警告，學到 CI 也需要維護。

### 限制

這個專案很小，只有六十幾行。真正的專案測試會複雜很多，可能需要接資料庫，或是跑一次就要好幾分鐘，這些我這次都沒有碰到。另外我只做了單元測試，整合測試和效能測試都還沒有嘗試。

### 心得

做這個主題之前，我覺得程式能跑出結果就算寫好了。這次發現，一支我自己寫、也交過作業的程式，居然有四類錯誤，最嚴重的「60 分被當」甚至在第一次執行時就印在畫面上了，只是我沒看到。這讓我理解為什麼課本一直強調測試要有系統地設計，而不是隨便丟幾筆資料試試看。

另一個感受是，有了測試以後，我比較敢改程式。整理等第表的時候，要是沒有測試，我大概會一直擔心改壞；這次改完跑一次，全部過了，就放心了。而 GitHub Actions 讓「記得跑測試」這件事不用再靠人記，我想這就是上課講的持續整合想解決的問題。

如果之後還有時間，我想補上姓名重複和欄位格式錯誤的測試，把程式碼風格檢查（例如 flake8）也加進 Actions，再試著用 Pull Request 的方式改程式，看看 Actions 怎麼在合併之前先把關。
