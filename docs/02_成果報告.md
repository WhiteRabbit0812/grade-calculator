## 一、學習內容與執行過程

### 1. 練習對象

大一寫的「成績計算小工具」`src/grade.py`，共 5 個函式：

| 函式 | 功能 |
|---|---|
| `average(scores)` | 計算平均 |
| `letter(score)` | 分數轉等第（A／B／C／D／F） |
| `gpa(scores)` | 計算 GPA（A=4 … F=0） |
| `load_csv(path)` | 讀取 `姓名,分數` 格式的檔案 |
| `report(path)` | 輸出每人等第與全班平均 |

### 2. 執行步驟（對照 Git commit 紀錄）

| 步驟 | 做了什麼 | Commit |
|---|---|---|
| ① | 把舊程式原封不動放進 Git，當作「修正前」基準 | `初始版本：成績計算程式（尚無測試）` |
| ② | 依邊界值分析設計測試案例，用 pytest 撰寫 22 個測試，並保存執行結果 `docs/test_before.txt` | `新增單元測試（目前 10 個失敗，找到 4 類 bug）` |
| ③ | 依失敗的測試逐一修正程式，順便把重複的 if 判斷整理成一張等第表 | `修正 4 類 bug、重構等第表；加入 GitHub Actions 自動化測試` |
| ④ | 撰寫 `.github/workflows/test.yml`，push 到 GitHub 後確認 Actions 自動執行 | （同上） |

### 3. 測試設計方式

對每個函式都考慮三種情況：**正常輸入、邊界值、錯誤輸入**。

- `letter`：每個等第門檻都測「剛好達到」和「差 1 分」，例如 90→A、89→B、60→D、59→F；另外測 -1 與 101 應該丟出 `ValueError`。這部分用 `@pytest.mark.parametrize` 一次寫 10 組資料，不用複製貼上 10 個函式。
- `average`、`gpa`：除了一般資料，也測「空串列」。
- `load_csv`：用 pytest 提供的 `tmp_path` 建立暫存檔，測正常檔案、含空白行與多餘空格的檔案、分數不是數字的檔案。
- `report`：測整體輸出是否包含正確的姓名、等第與平均。

### 2. 找到的 4 類 bug

| # | Bug | 原因 | 影響 |
|---|---|---|---|
| 1 | **剛好 90／80／70／60 分的等第少一級** | 用了 `>` 而不是 `>=` | 60 分的同學被判為 F（不及格），是最嚴重的錯誤；而且用範例資料手動執行時就出現過，但我當時沒注意到 |
| 2 | 沒有成績時程式當掉 | `average`、`gpa` 直接除以 `len(scores)`，空串列會 `ZeroDivisionError` | 空檔案就無法產生報表 |
| 3 | 不合理的分數（-1、101）沒有被擋下 | 沒有檢查輸入範圍 | 打錯的資料會被當成正常成績 |
| 4 | 檔案有空白行或多餘空格會當掉 | `line.split(",")` 前沒有 `strip()`，也沒跳過空行 | 用 Excel 匯出的 CSV 結尾常有空行，實際使用很容易遇到 |

另外，舊程式用 `open()` 開檔後沒有關閉，改成 `with open(...)` 寫法。

**修正後**：把門檻、等第、點數整理成一張表，兩個函式共用：

```python
GRADE_TABLE = [
    (90, "A", 4),
    (80, "B", 3),
    (70, "C", 2),
    (60, "D", 1),
    (0, "F", 0),
]

def letter(score):
    if score < 0 or score > 100:
        raise ValueError("分數必須介於 0 到 100：" + str(score))
    for lower, grade, _ in GRADE_TABLE:
        if score >= lower:
            return grade
```

**設計理由**：以後如果學校改成 A+／A-，只要改表格一個地方；之前門檻寫在兩處，很容易改了一邊忘了另一邊。因為已經有測試，重構完重跑測試就能確認行為沒變。

## 四、遇到的困難及解決方法

| 困難 | 解決方法 |
|---|---|
| 測試檔 `import grade` 找不到模組 | 程式放在 `src/` 資料夾，測試在 `tests/`，pytest 預設找不到。在測試檔開頭把 `src` 加進 `sys.path` 解決。之後查到也可以用 `pyproject.toml` 設定 `pythonpath`，是更正式的做法 |
| 不知道怎麼測「讀檔案」的函式 | 一開始想在專案放好幾個測試用 CSV，後來在文件中找到 `tmp_path`，可以在測試中臨時建立檔案，測完自動刪除 |
| Windows 終端機中文顯示成亂碼 | 設定環境變數 `PYTHONIOENCODING=utf-8` 後正常；也確認讀檔時有指定 `encoding="utf-8"` |
| 一開始以為「測試失敗 = 測試寫錯」 | 第一次跑出 10 個失敗時，我先懷疑自己的測試。逐一對照規則後才確定是程式的錯，例如學校規定 60 分及格，舊程式卻判成 F |
| 不確定 YAML 縮排是否正確 | 先複製 GitHub 官方的 Python 範本，再一步步修改；push 後在 Actions 頁面看 log 確認每個步驟都有執行 |

## 五、學習成果、限制與個人反思

**學習成果**

- 學會 pytest 的基本測試、參數化測試、例外測試與暫存檔用法
- 實際體會到邊界值分析的效果：這次找到的最嚴重 bug（60 分被判不及格）就是靠「剛好在門檻上」的測試找到的
- 會設定 GitHub Actions，讓測試在每次 push 時自動執行，並用覆蓋率門檻避免之後新增的程式沒寫測試

**限制**

- 專案很小（約 60 行），在真實的大型專案中，測試設計和 CI 設定會複雜很多（例如需要資料庫、測試時間很長）
- 只做了單元測試，沒有做整合測試或效能測試
- 覆蓋率 95% 只代表「這些程式碼有被執行過」，不代表所有情況都測過。例如 CSV 有三個欄位、姓名重複等情況，我目前還沒有測試

**個人反思**

做這個主題之前，我覺得程式「跑得出結果」就是寫好了。這次發現，一個我自認為很簡單、也交過作業的程式，竟然有 4 類 bug，其中「60 分被判不及格」甚至在範例資料裡就出現了，只是我當時沒仔細看。這讓我理解為什麼課本說測試要「有系統地設計」，而不是隨便丟幾筆資料看看。

另一個收穫是：有了測試之後，我比較敢修改程式。重構等第表時，如果沒有測試，我會很擔心改壞；但這次改完重跑一次、全部通過就放心了。GitHub Actions 則讓「記得跑測試」這件事不再依賴人，這應該就是課堂上講的持續整合想解決的問題。

如果之後有時間，我想繼續嘗試：（1）補上姓名重複、欄位格式錯誤等測試；（2）加入 flake8 等程式碼風格檢查到 Actions 中；（3）練習用 Pull Request 的方式提交修改，看 Actions 怎麼在合併前把關。
